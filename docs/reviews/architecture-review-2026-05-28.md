# Architecture Review — rusty-imap-mcp

> **Provenance.** Produced by a multi-agent review workflow on 2026-05-28: one
> reviewer per unit (the eight crates, with `rimap-server` split into
> `mcp` / `tools` / `boot+cli`), every finding re-checked by an independent
> verifier that re-opened the cited source. 31 of 40 raw findings survived
> verification; 3 cross-crate findings were added. The three **P0** findings
> shipped in **PR #328**. The remaining **7 P1** and **19 P2** findings are
> tracked as issues **#329–354** (one issue per item, labelled `P1`/`P2` +
> `tech-debt`). This document is the canonical writeup those issues reference.

## 1. Executive summary

- **Simplification (highest leverage):** Two crates carry phantom/dead public surface that misleads readers and the audit-grade error taxonomy. `rimap-smtp` ships three never-constructed `SmtpError` variants (one masking a real timeout misclassification) and an unused `SmtpClient::send` that leaks `lettre::Message` into the API; `rimap-imap` plumbs a `has_list_status` capability through five sites that never gates anything. Delete or wire these.
- **Simplification (security tables):** Security-critical policy tables are hand-mirrored in two crates — `rimap-audit`'s 24-entry `search`/`search_advanced` redaction tables and `rimap-server`'s `output_schema`/`tool_spec` `None` sets — each guarded only by an equality test plus an `expect`. Collapse each pair to a single source.
- **Separation of concerns (server boot):** `main.rs::run` (188 lines, with a standing `#[expect(too_many_lines)]`) braids subcommand routing, subsystem assembly, and the load-bearing MCP transport lifecycle. Split routing and assembly out; keep the `tokio::select!` shutdown choreography intact.
- **Separation of concerns (codec-in-handler):** Pure byte-format codecs live inside tool handlers — the mboxrd serializer inside `export_messages.rs` (1624 lines) and account-discovery network I/O + protected-folder policy inline in `build_registry`. Relocate the codec and the merge policy so they are independently testable.
- **Module organization (misplaced files):** `mcp/content.rs` is a content-pipeline adapter sitting under the MCP protocol module; `rimap-content`'s `raw_parts.rs`/`threading.rs` sit at crate root while violating the parse-subtree's "no direct mail-parser imports" invariant. Relocate to restore the declared boundaries.
- **Boundary optimization (visibility leaks):** Several items are wider than their callers need — `tool_catalog`/`TOOL_DEFS` are `pub` only for a test subcommand; export-internal seam types are `pub(crate)` but used only in-file; `RedactionSchema`'s `policies` map is publicly mutable on a security type. Tighten to the minimum visibility.
- **Boundary optimization (cross-crate facades):** Server handlers reach past `rimap-content`'s two pipeline front doors into `unicode`/`lookalike`/`html` internals, so the "sanitize every untrusted byte before returning" policy is enforced per-call-site. Narrow `rimap-content`'s public surface rather than adding a dispatcher.
- **Already healthy:** `rimap-core` (leaf domain types, `#![forbid(unsafe_code)]`) and `rimap-config` (mechanism cleanly separated from orchestration, consistent redaction/containment) need no structural change.

## 3. Cross-crate / boundary findings

### `rimap-content` → `rimap-server`: handlers bind to mechanism modules, not the two pipeline front doors (boundary-optimization, low)

`rimap-content` is designed around two outcomes — parse a message, sanitize HTML — but server handlers reach past that facade into low-level modules. `crates/rimap-server/src/tools/retrieval/search.rs` imports both `rimap_content::unicode` and `rimap_content::lookalike::analyze_addr_lookalike`, and other handlers pull `rimap_content::html::pipeline` and `sanitize_subject` directly. Each tool independently chooses which sanitizer to apply to its output, so the load-bearing "every byte of email is untrusted → sanitize before returning to the agent" policy is enforced per-call-site rather than at one boundary; a handler that forgets the right sanitizer silently returns unsanitized text.

Recommendation (keep low, no new dispatch abstraction): narrow `rimap-content`'s public surface. Demote the `unicode`/`lookalike`/`html` submodule internals behind the pipeline facade and expose only the small set of named display-sanitizers handlers legitimately need (e.g. a crate-root `sanitize_for_display` plus `analyze_addr_lookalike`). That makes the sanctioned call sites obvious without adding indirection. Only consolidate the per-tool sanitize sequences if the identical sequence recurs verbatim three or more times. This finding subsumes the per-unit `rimap-server::tools` placement of sanitizers — treat it once, here. (Tracked as #338.)

### `rimap-config` → `rimap-authz`: peer "support" crates have a real direction (module-organization, low)

The architecture description treats `config` and `authz` as peer cross-cutting support crates, but `crates/rimap-authz/Cargo.toml` depends on `rimap-config`, and `rimap-authz/src/matrix.rs:8` and `folder_guard.rs:14` both `use rimap_config::model::Verdict` while the guards read config's `ValidatedAccountConfig` DTOs directly. The dependency is acyclic and pragmatic — authz genuinely must read validated config plus the `Verdict` override type — so no restructuring is warranted. Record in the architecture doc that config is **upstream** of authz, not a peer, so a future config→authz back-edge (which would create a cycle) is not introduced by accident.

### `rimap-core` ↔ `rimap-imap`: folder-name validators duplicate the control-byte policy (simplification, low)

`rimap-imap` has two folder-name validators with deliberately different roles, and the split is sound: `ops/folder_management.rs:20` `validate_folder_name` correctly delegates to `rimap_core::FolderName::new` for CREATE/RENAME/DELETE/STORE input, while `ops/folders.rs:21` `validate_server_folder_name` is intentionally more permissive for server-returned LIST names (rejecting only control bytes, since bidi/zero-width are handled downstream by `rimap_content::unicode::sanitize`). The one smell: the permissive path hand-rolls its own control-byte loop (`folders.rs:22-29`, `b==0 || b<0x20 || b==0x7f`) rather than expressing "core's rules minus the bidi/zero-width checks", so if core tightens its control-char definition the two paths can silently diverge. Leave as-is unless the rules drift; if a future change touches the control-char rule, expose a single core predicate the permissive path can call. Do not add abstraction preemptively.

### rimap-audit
