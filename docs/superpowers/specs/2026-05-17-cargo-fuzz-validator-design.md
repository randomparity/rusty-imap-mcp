# cargo-fuzz target for `validate()`

## Purpose

Coverage-guided fuzzing of `crates/rimap-server/src/mcp/wire_validator.rs::validate()` to find classes of bugs the existing proptest cannot reach. The proptest runs against the full async harness at ~1 ms/case; libFuzzer running against the pure decision function runs at 100k–500k cases/sec with coverage feedback, so it explores the input space 5–6 orders of magnitude faster and biases toward inputs that hit new code paths rather than random samples.

The target is local-only and on-demand. CI integration is out of scope; the existing proptest nightly (`.github/workflows/mcp-fuzz-nightly.yml`) is sufficient for unattended regression coverage.

## Threat model

What we're trying to catch:

- Panics on inputs `validate()` doesn't expect — out-of-bounds, integer arithmetic, unwrap paths, recursion limits hit through deeply nested JSON.
- Grammar mismatches between `validate()` and rmcp's `RxJsonRpcMessage` deserializer: shapes the validator forwards that rmcp then rejects (the `is_forwardable_id` / `is_well_formed_error` class of bug Codex flagged on 2026-05-16).
- Resource-exhaustion patterns (pathological JSON triggering large allocations, super-linear time in `serde_json::from_str`).

What we are not testing here:

- Round-trip integrity of `synthesize_error_line` — covered by existing unit tests and out of scope per the brainstorm.
- Async/IO behavior of `validate_inbound` — needs a different fuzzing approach (a `tokio::io::DuplexStream` mock) and lives behind the proptest harness already.
- The three `is_*` helpers as separate targets — they are exercised through `validate()`.

## Architecture

### Layout

```
crates/rimap-server/
├── Cargo.toml                              # add [features] fuzzing = []
├── src/mcp/wire_validator.rs               # add fuzzing-gated re-export
└── fuzz/
    ├── .gitignore                          # generated by cargo fuzz init
    ├── Cargo.toml                          # depends on rimap-server features=["fuzzing"]
    ├── fuzz_targets/validate.rs            # the fuzz target
    └── corpus/validate/                    # ~20 seed envelopes (committed)
```

`crates/rimap-server/fuzz/` is a standalone workspace member that cargo-fuzz manages. It is NOT a member of the top-level workspace — cargo-fuzz's generated `Cargo.toml` carries `[workspace]` to break inheritance, which keeps the nightly toolchain and instrumentation contained.

### Visibility

`validate()` is `pub(crate)` and must stay that way for production builds. To expose it to the fuzz crate without widening public API:

1. Add an empty `fuzzing` feature flag to `crates/rimap-server/Cargo.toml`.
2. In `wire_validator.rs`, append a feature-gated `#[doc(hidden)] pub` re-export:

   ```rust
   #[cfg(feature = "fuzzing")]
   #[doc(hidden)]
   pub use validate as __fuzz_validate;
   ```

3. The fuzz crate depends on `rimap-server = { path = "..", features = ["fuzzing"] }` and calls `rimap_server::mcp::wire_validator::__fuzz_validate`.

Production builds (no `--features fuzzing`) see no API change. `cargo doc` hides the re-export. The feature stays off in all standard build paths as long as no other workspace member depends on rimap-server with `features = ["fuzzing"]` — only the fuzz subcrate does, and it lives in a separate workspace.

### Fuzz target

`fuzz_targets/validate.rs` body, eight lines:

```rust
#![no_main]
use libfuzzer_sys::fuzz_target;
use rimap_server::mcp::wire_validator::__fuzz_validate as validate;

fuzz_target!(|data: &[u8]| {
    if let Ok(s) = std::str::from_utf8(data) {
        let _ = validate(s);
    }
});
```

The non-UTF-8 skip is correct: `validate_inbound` rejects non-UTF-8 outright at the I/O layer (Codex finding #2), so `validate()` itself never sees malformed bytes in production. Feeding it non-UTF-8 would test code that cannot be reached.

The assertion is implicit — libFuzzer treats any panic, abort, or sanitizer report as a finding. No explicit `assert!` is required.

### Corpus seed

`corpus/validate/` ships with ~20 example envelopes, one per shape exercised in `wire_validator.rs::tests::*`. Examples (one file each, raw bytes, no trailing newline):

- `valid-request-numeric-id`, `valid-request-string-id`
- `valid-notification`
- `valid-response`, `valid-error-response`
- `parse-error-malformed-json`, `parse-error-truncated`
- `invalid-request-no-jsonrpc`, `invalid-request-wrong-jsonrpc`, `invalid-request-null-id`, `invalid-request-array-id`
- `params-as-array`, `params-as-null`, `params-as-number`, `params-as-string`
- `error-fractional-code`, `error-out-of-i32-code`
- `id-fractional`, `id-out-of-i64`
- `mixed-method-and-result`

These bootstrap libFuzzer's coverage map; the mutator discovers further structure from there. The initial seed corpus IS committed to the repo (it is part of the harness). Inputs libFuzzer discovers during runs accumulate in the same directory but are NOT committed by default — they are developer-local working state. If a particular discovered input has reproduction value, copy it into the seed corpus deliberately and `cmin` to deduplicate.

## Operation

### Local runs

```sh
# Quick smoke (1 min)
cargo +nightly fuzz run validate -- -max_total_time=60

# 1-hour focused run
cargo +nightly fuzz run validate -- -max_total_time=3600

# Overnight (8 h)
cargo +nightly fuzz run validate -- -max_total_time=28800
```

libFuzzer adds new interesting inputs to `corpus/validate/` as it discovers them. The corpus directory growing IS the point — it represents the validator's accumulated input coverage. Periodically running `cargo +nightly fuzz cmin validate` minimizes the corpus while preserving coverage.

### Findings

Crashes land in `crates/rimap-server/fuzz/artifacts/validate/<sha>` as raw bytes. Reproduce with:

```sh
cargo +nightly fuzz run validate crates/rimap-server/fuzz/artifacts/validate/<sha>
```

For every finding: convert the artifact to a `#[test]` regression in `wire_validator.rs::tests`, fix `validate()`, confirm the test fails before the fix and passes after, then keep the artifact in `artifacts/` for the historical record.

## Out of scope (deferred)

- CI integration. cargo-fuzz benefits from a long-lived growing corpus and dedicated runner time; the proptest nightly is sufficient for the regression-prevention story today.
- Sanitizer tuning beyond cargo-fuzz's defaults (ASan on; MSan/UBSan disabled).
- Fuzzing `synthesize_error_line`, the `is_*` helpers, or `validate_inbound`.
- Coverage report generation (`cargo +nightly fuzz coverage`); useful but a separate workflow.
- Wiring the proptest regression seeds (`mcp_wire_proptest.proptest-regressions`) into the corpus — those are harness-level inputs, not validator-level.

## Decisions log

- **Scope: `validate()` only.** The `is_*` helpers are exercised through it; the `synthesize_error_line` round-trip is covered by unit tests; `validate_inbound` needs async fuzzing which is its own design.
- **Input: raw `&[u8]` → `&str`.** libFuzzer's mutator discovers JSON structure from coverage feedback within minutes. An `Arbitrary`-driven structured-JSON target would skip the parse_error path entirely.
- **Feature flag, not `pub`.** Keeps production public API unchanged; idiomatic pattern for cargo-fuzz on internal symbols.
- **Local-only.** The proptest nightly already covers regression prevention; cargo-fuzz wants a dedicated runner and a growing corpus to be useful, which is a separate operational commitment.
