# ADR-0025: Pre-init validator interception restores single-envelope contract

**Status:** Accepted · 2026-08-21 · issue [#821](https://github.com/randomparity/rusty-imap-mcp/issues/821)

## Context

ADR-0024 documented the two-envelope behavior under rmcp 3.x: a pre-init non-ping/non-initialize request produces TWO envelopes — rmcp's `-32602` (from its pre-init `_meta` validation) and our `-32002` (from `#275` envelope synthesis) — in an unstable order. The `-32002` contract itself remained intact, but the race condition violated the MCP spec's deterministic single-envelope expectation and surfaced as test flakiness (#821).

The two-envelope design was chosen over validator interception because interception would add permanent bespoke logic to the security-sensitive transport layer solely to hide upstream behavior (#733 rationale). However, the follow-up issue #821 now demands restoration of the single-envelope contract: clients expect exactly one envelope for pre-init lifecycle violations, and the rmcp 3.x two-envelope path is a spec-drift artifact that should not leak to the wire.

## Decision

**Intercept pre-init requests in `wire_validator::inbound::validate_inbound`.**
Track initialization state; while uninitialized, a JSON-RPC REQUEST (has
forwardable `id`) whose `method` is neither `"initialize"` nor `"ping"` is
intercepted:

1. Synthesize the `-32002` envelope using the existing
   `preinit::synthesize_pre_init_error_envelope` machinery (id echoed verbatim,
   fixed opaque message, no `data` field).
2. Write the envelope directly to shared stdout (same path as
   `main.rs::emit_pre_init_error_envelope`). A write failure propagates with
   the same operator-facing context (`writing pre-init error envelope to
   stdout`) BEFORE any interception state changes.
3. Raise a shared `pre_init_intercepted` flag (`ValidatedStdio`).
4. Close the rmcp inbound duplex to signal EOF to rmcp (preventing it from
   seeing the request), then return `Ok(())`.

This approach prevents rmcp from observing the intercepted request entirely, so
its pre-init `_meta` validation never runs. The single `-32002` envelope is now
deterministic.

### Shutdown coordination

The key challenge (identified during #821 triage) is ensuring clean shutdown
after interception. Two naive designs fail:

- Returning `Ok(())` without coordination lets rmcp observe EOF-before-initialize
  and fail with `"MCP server init: connection closed: initialize request"`,
  producing a non-zero exit through the init-failure handler — which may also
  emit a SECOND `-32002` envelope.
- Signalling via a distinguished error returned by `validate_inbound`
  (surfaced through the supervisor's `JoinHandle`) is architecturally racy:
  closing the duplex wakes rmcp — and the init-race `tokio::select!` on another
  worker thread — while the bridge task is still mid-poll. In that window the
  task's `JoinHandle` is still pending, so no signal that travels AFTER the
  duplex drop can win the biased select deterministically (observed: the rmcp
  arm resolved with the EOF error while the bridge arm was still pending).

The solution makes the interception observable before the racy drop happens,
and consults it before interpreting the race result:

1. The inbound bridge raises `pre_init_intercepted` (an `Arc<AtomicBool>`
   handed back on `ValidatedStdio`) strictly before dropping the duplex.
2. `serve_mcp` loads the flag immediately after the init race resolves, before
   matching on which arm fired. If set, it takes the same drain +
   `supervisor.shutdown_after_failure()` cleanup as the failure arms but returns
   `ServeOutcome { result: Ok(()) }`, so `process_end.reason` stays `Eof` and
   the exit code stays 0. `drop(init_fut)` cancels rmcp before it can act on
   anything else.
3. If the envelope write fails, the flag was never raised, so every existing
   failure semantic is preserved: the error surfaces through the supervisor's
   bridge arm as a real failure (`process_end.reason: Error`, non-zero exit),
   pinned by `pre_initialize_envelope_write_failure_records_error`.


### Interaction with rmcp

Since rmcp never sees the intercepted request:
- No `-32602` envelope is generated by rmcp's pre-init `_meta` validation.
- The request is swallowed entirely at the validator layer.
- rmcp observes EOF on its read end and exits cleanly (since we dropped the inbound duplex).

## Consequences

- **Single-envelope contract restored:** Pre-init non-ping/non-initialize requests now receive exactly one `-32002` envelope, id echoed verbatim, with clean close (exit 0, `Eof` audit reason).
- **No -32602 leakage:** rmcp's pre-init validation never runs on intercepted requests, so no upstream error envelope reaches the client.
- **Test updates:** `tools_list_before_initialize` and `tools_list_before_initialize_str_id` now assert exactly ONE `-32002` envelope (no `-32602` pair, no order-agnostic assertion).
- **ADR-0024 superseded:** Mark ADR-0024 as `Superseded-by-ADR-0025` (amendment section).
- **No new runtime dependencies:** Uses existing `preinit::synthesize_pre_init_error_envelope` and shared stdout locking.
- **Minimal validator changes:** Adds an initialized flag and the shared
  `pre_init_intercepted` flag to the existing `validate_inbound` loop; no new
  transport paths or abort coordination. `main.rs::serve_mcp` gains one
  flag-check exit before interpreting the init race.
